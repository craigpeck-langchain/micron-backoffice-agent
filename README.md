# Micron Back-Office Agent Demo

A demo built for LangChain's "art of the possible" conversation with Micron's
VP of AI Finance and Automation, modeled on C.H. Robinson's production
pattern: turning ~15,000 inbound emails/day into ~5,500 structured shipping
orders, generalized here to invoices, purchase orders, and remittance
advice. It's built to showcase two things at once - **LangGraph + deep
agents** as the orchestration/execution layer, and **LangSmith Engine** as
the mechanism that turns production traces into found bugs, proposed
fixes, and new eval cases without anyone pre-telling it what's wrong.

## 1. What the agent does

The agent is an email intake pipeline for a back-office team: point it at
an inbound email (from a vendor, an internal requester, or a payer) and it

1. **Classifies** the email into one of four document types - shipping
   order, purchase order, invoice, or remittance advice - or flags it as
   out of scope.
2. **Delegates** to the document-type-specific handler, which extracts the
   relevant structured fields (vendor, line items, amounts, dates, etc.).
3. **Validates** what it extracted against a mock ERP (vendor records,
   open POs) before taking any action.
4. **Acts**: posts the record (shipping order / PO / invoice / remittance
   match), or - when something doesn't check out - escalates to a human
   with a ticket, or asks the sender a clarifying question.

Every run is fully traced in LangSmith. The interface is a Micron-branded
chat UI with a sample-email "inbox" sidebar (grouped by document type,
filterable to just the ones with a planted flaw) so a presenter can click
an email instead of typing one.

## 2. Main components

| Component | What it is | Where |
|---|---|---|
| Top-level graph | A plain LangGraph `StateGraph`: `ingest_email -> classify_document -> (deep_agent \| request_clarification)`. Deterministic, cheap, and traced as its own span - this is the "LangGraph orchestration" half of the demo. | `src/backoffice_agent/graph.py` |
| Classifier | A structured-output LLM call (not agentic) that decides the document type. Carries the wrong-tool-classification flaw (see below). | `src/backoffice_agent/classify.py` |
| Deep agent | One `deepagents.create_deep_agent(...)` call, embedded as a single node in the top-level graph. Owns planning (`write_todos`), a virtual filesystem (writes the raw email to `email.txt` for anyone reviewing the trace), and delegates to one of four subagents via its built-in `task` tool. This is the "deep agents" half of the demo. | `src/backoffice_agent/graph.py` |
| Subagents | One per document type, each with its own system prompt and a scoped tool list (least-privilege): `shipping_order_agent`, `purchase_order_agent`, `invoice_agent`, `remittance_agent`. | `src/backoffice_agent/subagents/` |
| Shared tools | `lookup_vendor`, `lookup_open_po`, `validate_against_erp`, `escalate_to_human`, `request_clarification`, plus `list_open_pos_for_vendor` (invoice-only). All deterministic, mocked against `mock_data.py`. | `src/backoffice_agent/tools.py` |
| Mock ERP data | Vendors, open POs, ship-to sites - hand-shaped so specific flaws are reliably reproducible (e.g. two similarly-named vendors, one EUR-only vendor). | `src/backoffice_agent/mock_data.py` |
| Frontend | Vite + React + `@assistant-ui/react` + `@assistant-ui/react-langgraph`, talking to the LangGraph server via `@langchain/langgraph-sdk`. Served same-origin by a small FastAPI app (`app.py`) mounted via `langgraph.json`'s `http.app`. | `frontend/` |
| Fixtures | 50 synthetic emails (30 normal + 14 flaw-triggering + 6 out-of-scope), the source of truth for both the frontend's sample inbox and `populate_traces.py`. | `fixtures/emails/`, generated by `scripts/generate_synthetic_emails.py` |
| Evals | A 16-example golden dataset plus LLM-as-judge evaluators (hallucination, expected-behavior) and an `aevaluate` runner. | `evals/` |

Run it with `uv run langgraph dev` (agent + UI at `http://localhost:2024/inbox/`).

## 3. Purposely injected failure modes

Seven flaws are deliberately planted so LangSmith Engine has real,
reproducible issues to cluster from production traces - each mapped to a
category from Engine's own detection taxonomy (IssueBench). Two examples
of each are in `fixtures/emails/` (tagged `planted_flaw` in the fixture
JSON and in each trace's metadata).

| # | Flaw | Where it lives | IssueBench category |
|---|---|---|---|
| 1 | Invents a plausible-but-wrong PO number when an invoice references "a recent shipment" without stating one, using `list_open_pos_for_vendor` to grab *a* PO rather than asking | `subagents/invoice.py` prompt + tool | **Hallucination** |
| 2 | Posts an invoice without checking that its stated currency matches the vendor's ERP-recorded currency | `subagents/invoice.py` (`post_invoice`) | **Silent tool error** |
| 3 | `escalate_to_human` silently drops the ticket (still returns a success payload) when the vendor name contains `&` or `'` - an unescaped-string bug in the mock ticketing backend | `tools.py` | **Failed error recovery** |
| 4 | The classifier force-labels an email as `purchase_order` whenever the subject contains the word "order," even when the body is clearly an invoice against an existing PO | `classify.py` | **Wrong tool** |
| 5 | No tool exists for an invoice with a partial credit/return line - the agent either escalates every time or silently posts an amount that doesn't represent the credit | *(intentional gap - no tool)* | **Missing capability awareness / Feature gap** |
| 6 | `lookup_vendor` returns an unresolved "ambiguous" result with no candidate names when a query matches more than one vendor (e.g. two near-identical "Cascade Precision ..." records) - nothing tells the agent how to break the tie | `tools.py`, `mock_data.py` | **Agent looping** |
| 7 | The invoice subagent is told to trust the vendor's stated total over recomputing the line-item sum, so a padded/incorrect total goes through unquestioned | `subagents/invoice.py` prompt | **System prompt drift** |

The 6 out-of-scope fixtures (customs inquiry, non-English invoice, garbled
OCR text, a vendor relationship notice, marketing email, misdirected HR
email) have **no corresponding code bug** - they exist purely to give
Engine "missing capability" / "task evasion" signal for things the system
was never built to handle (e.g. no non-English or OCR-garbled document
support).

Note: these are LLM-driven behaviors, not hardcoded outcomes, so a given
run may resolve more gracefully than intended (e.g. escalating cleanly
instead of hallucinating) - that variability is realistic and still gives
Engine multiple distinct failure signatures to find across the 50 traces.

## 4. Demo flow / best practices

**Before the meeting:**
1. `uv run python scripts/populate_traces.py` to (re-)seed the LangSmith
   project with all 50 fixture runs, tagged and feedback-scored.
2. Open the LangSmith project's **Engine** tab and give it time to
   analyze - do this at least a day ahead, not live for the first time in
   the room. Re-run `populate_traces.py` (fully idempotent/re-runnable) to
   add volume if a flaw hasn't clustered clearly yet.
3. Restore + run the golden eval suite once so you have a clean
   experiment link ready to show:
   `uv run python evals/dataset_snapshot.py restore golden --reset`
   `uv run python evals/run_experiment.py golden`
4. Click through the UI yourself with a few sample emails so the flow is
   familiar, and confirm `LC_GATEWAY_KEY` / `LANGSMITH_API_KEY` are set in
   your shell or `.env`.

**In the room, a suggested narrative arc:**
1. **Frame it with C.H. Robinson.** ~15,000 emails/day -> ~5,500 shipping
   orders, generalized here to invoices/POs/remittance advice - the same
   read -> extract -> validate -> post -> escalate pattern.
2. **Show the build**, briefly: LangGraph doing deterministic
   intake/classification/escalation, a deep agent doing planning +
   delegation + extraction via subagents - point at the trace tree in
   LangSmith to show both are visibly separate, inspectable spans.
3. **Run a clean example live** (e.g. a normal invoice or shipping order
   from the sample inbox) to show the happy path end-to-end, then open its
   trace in LangSmith.
4. **Run one or two flaw examples live** (use the "Flaws" filter in the
   inbox sidebar) - the hallucinated-PO and ambiguous-vendor scenarios
   demo well since the model's reasoning is visible in the trace.
5. **Pivot to Engine.** Open the Engine tab on the pre-populated project:
   show the clustered issues, a Proposed Fix, and the auto-generated
   Offline Examples for one issue - this is the centerpiece. Tie it back
   to the golden eval experiment as the "how you keep it fixed" half of
   the story.
6. **Close on the unit-economics point**: per-step latency/token
   visibility in every trace is what keeps cost-per-document a number you
   manage, not discover after the fact.

**Talking points if asked about scope:** this is a demo harness, not a
production system - the ERP, ticketing, and posting tools are all mocked
and deterministic by design, so the focus stays on agent behavior and
observability rather than integration plumbing.
